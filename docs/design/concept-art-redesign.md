# AI Project 002 — コンセプトアート準拠・再設計

2026-09-12 / Visual & Experience Design v2

> この文書は、6作品の「画面の見え方・情報設計・プレイ導線」の最新版を定義する。
> ゲームロジックの基礎は [`game-evolution.md`](game-evolution.md) を引き継ぎ、今後の画面改修は本書と各作品別再設計書を優先する。

## 0. North Star

6作品を「ブラウザで動く試作」ではなく、**一目で遊び方が伝わり、触った瞬間にゲームとして成立して見える小さな完成品**へ引き上げる。

今回のコンセプトアートで確定した方向は、装飾を増やすことではない。以下を同時に成立させることが目的。

1. 画面を見た1秒以内に「何をするゲームか」が分かる。
2. プレイ中、常に「今の状態」「次にやること」「得られるもの」が分かる。
3. 主役となるキャラクター・戦場・大釜・カードなどがUIより先に目に入る。
4. 入力 → 結果 → 報酬 → 次の目標が1画面の中でつながる。
5. WebのカードUIではなく、各ジャンルのゲームUIとして見える。

## 1. 参照ビジュアル

2026-09-12の設計セッションで作成した **「AI Project 002 – Screen Concept Art」6画面ボード**を基準ビジュアルとする。生成元画像はチャット側の制作アセットとして保持し、本リポジトリでは本書と作品別仕様に、再現すべき画面原則を文章化して固定する。

この画像は完成画面そのものではなく、**画面密度・主役の大きさ・HUD階層・ゲームらしい情報配置の基準**として使う。

完全再現はしない。現在の実装・レスポンシブ・操作性を優先しながら、以下の要素を抽出する。

- 大きな主役ビジュアル
- ジャンルに合ったHUD文法
- 進行・目標・報酬の常時表示
- 主要アクションの強いCTA
- 画面内の奥行きとレイヤー
- キャラクター・背景・UIの一体感

## 2. 全作品共通の画面ルール

### 2.1 情報を3層に分ける

**Top / Status**
- 章・WAVE・年・ラウンド・制限時間
- HP / スコア / 通貨 / 生産量など、継続判断に必要な状態
- Pause / Settingsなどの補助操作

**Center / Playfield**
- そのゲームで最も見せたい対象を最大化
- 戦闘、選択、調合、マップ、カード判定など「プレイそのもの」を置く
- 説明文や補助パネルで中央を潰さない

**Bottom or Side / Action & Next**
- 主操作
- 次の目標
- 報酬予告
- 装備・スキル・選択肢など、プレイヤーが次に触るもの

### 2.2 画面の主役は1つ

各作品で最初に見せる対象を固定する。

| 作品 | 主役 |
|---|---|
| 三国ポチポチ | 戦略マップ / 関門・戦地 |
| 剣戟の森 | 主人公と敵がぶつかるプレイフィールド |
| ポーション工房 | 錬金術師 + 大釜 |
| 覇拳伝 | 2人の格闘家の対峙 |
| カルマクエスト | 主人公 + 世界 + 選択 |
| カラーマッチ | 判定対象カード |

### 2.3 常に「次」が見える

HUDには少なくとも1つ、未来情報を置く。

- 次ステージ / 次地点
- 次ルール切替
- 次に買える設備
- 奥義まであと何％
- 次の報酬
- 今の選択がどこへ影響するか

### 2.4 報酬を事前に見せる

プレイヤーが行動する前に、「成功すると何が得られるか」を提示する。

報酬は数値だけでなく、アイコン・装備・キャラクター・工房発展・章解放など視覚で見せる。

### 2.5 操作UIはゲームジャンルの文法に合わせる

共通部品で揃えすぎない。

- 格闘: 円形アクションボタン / HPバー / ラウンド
- アクション: スティック / スキル / BOSS HP / COMBO
- 放置: 生産設備カード / Upgrade / Mission / Progress
- シミュレーション: サイドメニュー / マップ / 編成 / 出陣
- 選択RPG: 会話 / 選択肢 / 評価メーター
- パズル: SCORE / TIME / CHAIN / 大型カード

統一するのは品質と階層であり、見た目を同じにすることではない。

## 3. ビジュアル品質基準

### キャラクター
- 主役は画面の15〜35%程度を占める。
- 顔や姿勢が分かる大きさを優先する。
- 主要画面でプレースホルダー図形を主役にしない。

### 背景
- 1枚絵をそのまま敷くだけでなく、前景 / 中景 / 遠景のレイヤーを意識する。
- UIの後ろは局所的に暗くする・明るくするなど、可読性を背景側で支える。

### UI
- パネル数を増やすより、重要度をサイズで表現する。
- 大数字（SCORE / COMBO / TIME / GOLD）はゲームらしい視認性を持たせる。
- CTAは画面内で1〜2個に絞り、最重要操作を最大化する。

### フィードバック
- 成功: scale / flash / particle / number / sound
- 危険: warning / border / shake / color shift
- 報酬: icon reveal / count up / chest / unlock
- 成長: before → afterが比較できる

## 4. レスポンシブ方針

デスクトップとスマートフォンで同じレイアウトを縮小しない。

- 縦型作品（Potion / Karma / Color）は390px幅を第一基準とする。
- 横型作品（Fist / Side Scroller）は800×600前後を第一基準とし、スマホでは横持ちまたは操作領域の再配置を許容する。
- Sangokuは縦型戦略画面を基準にし、マップ・編成・CTAが1スクリーンで読める密度を守る。

## 8. Definition of Done

各作品の画面改修は、以下を全て満たして完了とする。

- 初見で主要操作を説明なしに発見できる。
- 現在値だけでなく次目標が表示される。
- プレイフィールドまたは主役ビジュアルが画面の最大要素になっている。
- 最重要CTAが他UIより明確に強い。
- 成功・失敗・報酬の視覚フィードバックがある。
- 390px幅または想定横画面で操作可能。
- lint / typecheck / unit test / buildが成功。
- Playwright対象作品はブラウザE2Eが成功。
- 最終確認は実スクリーンショットでコンセプトアートと並べてレビューする。

## 9. 今後の進め方

以後のPRは、機能単位ではなく**画面の完成状態**を単位に切る。

例:

- `feat(potion): rebuild workshop main screen`
- `feat(sangoku): make campaign map the primary play screen`
- `feat(side): rebuild combat HUD and stage framing`

「HUDだけ」「影だけ」のような細切れPRを続けず、1PRで1画面を目標状態まで持っていく。
