# 仕様・設計を更新し続けるワークフロー

対象は6ゲーム、共通コード、配信・CI・ハブ。正本の入口は [current](current/README.md)。担当はその変更を実装する人／AI、内容確認はPRレビュー担当。

## 毎回の手順

1. 着手時に対象のspec.mdとdesign.mdを読む。現行仕様・将来案・不具合を分け、変える振る舞いと完了条件を決める。
2. 実装と同じブランチで、変わった仕様・設計の本文を更新する。旧説明への追記だけで矛盾を残さない。
3. docs/updatesに一意な名前のJSONを追加する。対象領域ごとに仕様／設計をupdatedまたはunchangedと宣言し、理由を書く。
4. 対象テスト・スクショ等の検証結果と未確認事項を記録する。数値はその実行の証拠へ結び付ける。
5. コミット後に下記ローカル検査を実行し、PRテンプレートを記入する。CIのDocumentationチェックも確認する。
6. レビューでは「コードと文書の意味が一致するか」「影響なしの判断が妥当か」を確認する。マージ・公開後の状態はリリース資料へ反映する。

## 更新先の判断

| 変更 | 仕様書 | 設計書 | 追加確認 |
| --- | --- | --- | --- |
| ゲームルール・操作・表示・数値バランス | 更新 | 責務・実装契約が変われば更新 | 受入条件・スクショ |
| 保存キー・データ形式・移行 | 更新 | 更新 | 旧セーブ・破損・復旧 |
| 読込・回転・非同期・SDK | 利用者の挙動が変われば更新 | 更新 | 二重処理・失敗時挙動 |
| リファクタ・依存更新・テスト | 挙動不変なら理由付きunchanged | 構成不変なら理由付きunchanged | 回帰結果 |
| 素材差替え | 世界観・UI契約への影響を判断 | 配置・読込の影響を判断 | manifest・容量・実画面 |
| CI・配信・共通コード | platformを評価 | platformを評価 | 影響する作品も個別評価 |

共通コード変更はplatformの記録を必須とし、作品固有の動作が変わる場合はその作品の記録・本文も追加する。この影響の意味判定はレビュー責務。
新作はdocs-policy.jsonへ登録し、spec.mdとdesign.mdを追加する。gameフォルダだけ追加するとCIは失敗する。

## 変更記録

ファイル例: docs/updates/2026-10-20-karma-loading.json。JSONのみを機械検査する。記録を過去PRから使い回さず、各PRで新規追加する。

```json
{
  "summary": "依頼画像の再試行中の表示を改善",
  "areas": {
    "karma-quest": {
      "spec": {"status": "updated", "reason": "再試行中に表示する文言と操作可能状態を更新した"},
      "design": {"status": "unchanged", "reason": "既存の読込状態と入力ガードを利用し、責務と保存形式は変えない"}
    }
  },
  "validation": ["関連E2Eとスクショの結果・保存先を具体的に記載"],
  "limitations": ["実機確認は未実施"]
}
```

updatedは対応する文書ファイルの差分を必須とする。unchangedは10文字以上の理由を必須とする。両方とも理由は具体的に書く。
日付や検証数を見せかけの更新として変更しない。文章の妥当性はCIだけでは判定できない。
同じ領域について複数の記録がある場合、updatedが一つでもあれば本文差分が必要。仕様書だけ変えて設計書を触らない場合も、設計への影響を記録する。

## ローカル検査

Python 3.11以上、Gitのみ。ゲームのnpm依存は不要。

```powershell
python -m unittest discover -s scripts/tests -p "test_docs*.py"
python scripts/check_docs.py --base origin/main --head HEAD
```

比較基点は自動でmerge-baseを使う。積み重ねPRではorigin/mainを対象PRのbaseブランチに置き換える。
検査はコミット済みのGit内容を読む。未コミットの変更を検査済みと誤認しない。スクリプトはコミット・push・文書生成をしない。
CIが動く前のPRや緊急修正にも、同じ手順で変更記録を残す。依存更新Botも例外扱いせず、レビュー担当が影響確認と記録を追加する。

## 検査の限界と導入

CIは文書の存在、対象領域、変更記録、updatedの差分、ローカルリンクを検査する。仕様がコードと一致するか、実機で良いかは自動認定しない。
初回導入以前の履歴に記録を遡って要求しない。以後のPRは同じコミット群に文書と記録を含める。
運用をマージ制約にするには、GitHubの保護ルールで「Documentation / documentation」を必須化する。設定権限が必要であり、文書作成時点で自動設定済みとは扱わない。
